## 三、技术架构

### 3.1 双驱动数据库：既能零安装演示，也能对齐项目书架构

项目书写的是 `MySQL + Redis`。为了在**没装 MySQL 的电脑上也能跑**（学校机房、评审笔记本），
代码里做了驱动抽象，业务逻辑只调用 `query / get / run / withTransaction`：

| 能力 | 默认（零安装） | 项目书架构（生产） | 切换方式 |
|---|---|---|---|
| 主数据库 | `node:sqlite`（Node 内置） | MySQL 8（阿里云 ECS） | `DB_DRIVER=mysql` |
| 缓存 | 进程内 LRU + TTL | Redis | `CACHE_DRIVER=redis` |
| 容器化 | — | Docker + Kubernetes | 项目书 3.3.1 规划 |

```bash
# 切到项目书描述的真实架构（本机已装 MySQL/Redis 时）
DB_DRIVER=mysql MYSQL_HOST=127.0.0.1 MYSQL_USER=root MYSQL_PASSWORD=xxx \
CACHE_DRIVER=redis npm start
```

**已实测**：MySQL DDL 由 `mysql-ddl.mjs` 自动从 SQLite schema 转换（TEXT→LONGTEXT/VARCHAR(191)、
AUTOINCREMENT→AUTO_INCREMENT），两套驱动共用同一份表结构与全部业务 SQL（统一 `?` 占位符）。

### 3.2 一物一码溯源（对应项目书 3.3.2 / 4.2.2）

| 项目书要求 | 实现 |
|---|---|
| 唯一加密二维码赋码 | 每个单品一个 `trace_code`（`CY` + 日期 + 随机位） |
| 基于椭圆曲线数字签名算法 | ECDSA / secp256k1 对 `溯源码\|批次号\|检验编号` 签名，写入二维码 token |
| 复制二维码无法伪造 | 扫码后服务端验签，篡改 token 立即判定为仿制品 |
| 基于区块链的全流程数据存证 | 每个节点 `hash = SHA-256(前序哈希 \| 节点内容)`，形成哈希链；查询时逐节点重算比对 |
| 可视化时间轴 | 原料产地环境 → 果实采摘 → 冷榨加工 → 成品检测 → 无菌灌装 → 物流配送 |
| 首次查询防伪 | 记录 `scan_count`，首次提示"正品"，重复查询提示已查询次数并提示二次封装风险 |
| 检测报告可点开 | 电子质检报告页面（演示用示例报告，正式上市需替换为 CMA/CNAS 真实报告） |

### 3.3 AI 智能客服（对应项目书 4.2.2 与表17）

- **NLP 意图识别**：五类意图（产地环境 / 产品安全性 / 产品功能与功效 / 抚触科普与用量 / 订单物流与售后）
  \+ 独立的**婴儿症状适用性**意图；采用关键词加权打分，命中越长越具体的关键词权重越高。
- **多轮对话状态管理**：抽取槽位（宝宝月龄、症状名、持续时间、部位），缺槽位时主动追问。
- **五大类标准应答策略**：直接对应项目书表17，并支持卡片消息（检测报告、溯源入口、教程、订单、商品）。
- **情感分析转人工**：识别愤怒/焦虑关键词与感叹号密度，命中即标记情绪并携带对话上下文转人工。
- **医疗安全红线（重点）**：见下节。
- **大模型可选增强**：配置 `AI_API_KEY` 后启用 OpenAI 兼容接口（默认 DeepSeek）；
  大模型**只负责话术润色，不参与症状适用性判断**，规则引擎始终掌握安全结论；调用失败自动回退。

### 3.4 关于「婴儿症状能不能用我们的产品」——医疗安全设计

这是用户最关心、也最容易出风险的场景，因此做了四级分级与强制免责：

| 级别 | 含义 | 触发示例 |
|---|---|---|
| `ok` | 皮肤完整、轻度，可正常使用（仍需小面积试用） | 干燥、起皮、头垢、轻度痱子 |
| `caution` | 需谨慎，建议先咨询医生，避开患处 | 湿疹、红臀/淹红、口水疹 |
| `avoid` | 患处禁用，完好皮肤可正常抚触 | 破皮、渗液、糜烂、裂口 |
| `emergency` | **先就医**，诊断前不要涂任何护肤油 | 发热、化脓、精神差、拒奶、呼吸异常、皮疹大面积快速扩散 |

强制约束：诊断结论与用药方案一律不给；每条症状回答附带免责声明；
命中红线时**跳过**大模型润色以确保安全措辞不被改写；同时把该会话标记为需人工跟进。

## 四、验证与自检（全部为真实执行结果）

```bash
cd chayaya/backend
npm run qr:check     # 二维码：生成 → 用独立解码器 jsQR 回读校验 + 防伪签名篡改测试
npm run smoke        # 端到端：注册→加购→结算→下单→支付→分配溯源码→扫码验签→AI问答→后台发货
npm run ui:check     # 前端：Node 模拟 DOM 真实执行前端模块，逐页断言渲染内容
npm run serve:check  # 静态托管：根路径是否返回应用入口、启动后是否真的渲染（而非停在骨架屏）
npm run link:check   # 链接巡检：把各页面渲染出的 href/src 全部请求一遍，杜绝"点进去 404"
npm run verify       # 五件事一起跑
```

当前结果：

| 自检 | 结果 |
|---|---|
| 二维码链路（含中文、长签名、纠错等级 H） | 5/5 通过，防伪签名可正确拒绝篡改 |
| 端到端业务链路 | 27/27 通过 |
| 前端页面渲染 | 11/11 页面通过 |
| 静态托管与应用启动 | 20/20 通过 |

> `serve:check` 与 `link:check` 是专门用来防「浏览器打开只有一个加载页」「点进去 404」这类问题的：

> 后者把渲染结果里出现的每个 href/src 都真实请求一遍。

## 六、常见故障排查

| 现象 | 原因与处理 |
|---|---|
| 打开页面一直停在「正在加载」 | 根路径被 `backend/public/index.html` 占位页挡住了。服务端已强制「根路径只由 `frontend/index.html` 提供」，若仍出现请删除 `public/` 下的 index.html，再执行 `npm run serve:check` 定位 |
| 访问 `/admin` 报 404 | 正确地址是 **`/admin.html`**；`/admin`、`/admin/`、`/bg` 现已自动 302 跳转到 `/admin.html` |
| 某入口点进去 404 | 执行 `npm run link:check`，它会把各页面渲染出的所有链接真实请求一遍并列出失效项 |
| 接口全部报错 | 确认后端在跑：浏览器访问 `/api/health` 应返回 `{"code":0,...}` |
| 数据被演示改乱 | `npm run reset` 一秒恢复干净演示数据（会重新生成 100 个一物一码） |
| 换到 MySQL/Redis 后连不上 | 检查 `DB_DRIVER=mysql` 时的 `MYSQL_*` 环境变量；Redis 连不上时系统会自动降级为内存缓存并打印告警 |
| 评审电脑不联网 | 全流程离线可用：二维码、溯源验签、AI 客服均为本地实现，不依赖外网 |
