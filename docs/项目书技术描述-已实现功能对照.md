## 五、关键实现取舍说明（评审可能的追问）

**1. 为什么前端没用 Vue/React？**
项目书原文是"采用 Vue.js 或 React"。实测环境中 npm 可用，但为了做到**双击即开、零构建、无网络依赖**
（学校机房与评审电脑普遍不联网），改用原生 ES Module + 手写 hash 路由实现了同等响应式效果，
页面结构与视觉完全延续团队自己的小程序 UI 原型（报告书图19）。同时按原计划导出了标准微信小程序工程，
拿到 AppID 后可直接上架，**不影响项目书技术路线的成立**。

**2. 为什么默认用 SQLite 而不是 MySQL？**
本机未安装 MySQL/Redis。为不改动项目书架构，实现了驱动抽象层：业务代码只依赖统一接口，
`DB_DRIVER=mysql` 一键切换。MySQL DDL 由脚本从同一份 schema 自动转换，
两套驱动共用全部业务 SQL，**切换无需改一行业务代码**。

**3. 自研二维码编码器为什么换成 npm 的 `qrcode`？**
最初自研了标准 QR 编码器，自检时发现数据排布缺陷（jsQR 无法回读）。
溯源二维码是打印到瓶身、要真扫得出来的关键环节，因此改用零运行时依赖的 `qrcode` 包，
并用独立解码器 jsQR 做回读验证（`npm run qr:check`，5/5 通过）；
自研版本保留为离线环境的图形码回退，页面上会明确显示当前使用的渲染器。

**4. AI 客服的医疗边界怎么保证？**
规则引擎负责所有安全判断，大模型只做话术润色；命中医疗红线时**跳过润色**，
避免安全措辞被改写。四级分级、红旗关键词、免责声明都集中在
`backend/src/data/knowledge-base.mjs`，可审计、可后台维护。
