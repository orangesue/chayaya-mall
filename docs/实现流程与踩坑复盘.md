## 第 1 章 总览：做了什么、用了什么

### 1.1 从项目书里"提取需求"是第一步

拿到的是 4 个文件：项目报告书（PDF + docx 源文件）、路演 PPT（PDF + pptx 源文件）。
PDF 里的中文字体是 CID 编码，无法直接复制文字，所以我改用 **docx/pptx 源文件**提取（本质是 zip + XML）：
自己写了个 Python 脚本解析 `word/document.xml`，按顺序抽取段落、**表格**和**图片**，
得到一份带图片位置标记的纯文本，这样才看清了项目书的完整结构。

**关键结论（技术需求全部来自项目书本身，不是我编的）**：

| 项目书位置 | 原文要求 | 我把它做成了什么 |
|---|---|---|
| 3.3.1 建设多渠道线上商城 | Vue/React 响应式网页；登录注册、商品展示（分类/详情/**AI 推荐**）、购物车与订单（**实时库存同步**）；Node.js 后端；MySQL 主库 + Redis 缓存 + MongoDB 日志；支付集成 | 前端响应式 + 完成购买闭环 + 库存流水 + 双驱动数据库 |
| 3.3.2 扫码溯源 | 一物一码加密二维码；云端存证；**时间轴**展示种植→加工→物流；电子质检报告 | 100 个溯源码 + 时间轴 + 报告页 + 首次查询防伪 |
| 4.2.2 区块链可信溯源 | **椭圆曲线数字签名**（ECDSA）防复制；**哈希值同步存证**、扫码时链上比对 | ECDSA/secp256k1 签名 + SHA-256 哈希链 + 篡改检测 |
| 4.2.2 AI 智能客服 | **NLP 意图识别**（功效/安全性/使用方法/订单物流）；**多轮对话状态管理**；表17 五大类应答策略；**情感分析**转人工 | 6 类意图 + 槽位追问 + 知识库 16 条 + 情绪转人工 |
| 3.2.1 会员体系 | 新芽→成长→守护 三级，按累计消费升级 | 会员等级自动升降 + 权益 |
| 5.1 运行与维护 | 数据维护、月度运维总结、分龄护肤知识 | 埋点 + 销售漏斗 + 月度报告 + 分月龄抚触教程 |

**额外的、项目书没写但用户最关心的需求**：用户在问"宝宝有某种症状，能不能用我们的产品"——
这是医疗风险场景，我做了**症状四级分级 + 医疗安全红线**（详见 3.5）。

### 1.2 动手前先探测环境（这一步省了后面很多返工）

| 依赖 | 探测结果 | 对方案的影响 |
|---|---|---|
| Node.js | v24.21.0 ✅ | 可用；且自带 `node:sqlite`，实现了零安装数据库 |
| MySQL / Redis / Docker | ❌ 全部未安装、端口无监听 | **不能只写 MySQL 版本**，否则交付物在本机跑不起来 |
| 外网（npm registry） | 一开始探测不通，后来恢复 | 促成了"能离线跑"的设计取向 |
| Node 内置 sqlite | 实测可用 | 定为默认驱动 |
| git / GitHub SSH | 已装；SSH 认证成功（账号 orangesue） | 后期可直接推 GitHub |

**这一步的教训**：先探测再设计。如果直接按项目书写 MySQL 版，交付当天会因为跑不起来而全部返工。

### 1.3 技术选型与理由（答辩高频问题）

| 层面 | 实际选择 | 为什么不选项目书里写的那个 |
|---|---|---|
| 前端 | 原生 ES Module + 手写 hash 路由 + 原生 CSS | 项目书写 Vue/React。为了做到**双击即开、零构建、不联网也能跑**（机房/评审电脑普遍不联网）；同时**另外导出了标准微信小程序工程**，拿到 AppID 可直接上架，技术路线不受影响 |
| 后端 | Node.js 内置 `node:http`，零框架 | 项目书只要求 Node.js；不用框架的好处是依赖极少、启动快、全链路可读 |
| 数据库 | 抽象层：`node:sqlite`（默认）↔ MySQL（生产） | 项目书要求 MySQL 但本机没有；做成**双驱动**，`DB_DRIVER=mysql` 一行环境变量切换，**业务代码零改动** |
| 缓存 | 抽象层：进程内 LRU+TTL（默认）↔ Redis | 同上；Redis 连不上时自动降级并告警 |
| 二维码 | npm `qrcode`（自研版保留为离线回退） | 见 3.2：自研编码器有缺陷，溯源二维码必须"印出来真能扫" |
| 防伪签名 | `node:crypto` 的 ECDSA(secp256k1) | 项目书原文就是椭圆曲线数字签名 |
| 存证 | `node:crypto` 的 SHA-256 哈希链 | 项目书说"哈希值同步存证 + 扫码比对"，本地哈希链完整实现了这个校验逻辑 |
| AI 客服 | 规则引擎为主 + 可选大模型润色 | 项目书写 NLP；规则引擎离线可用、结果可复现、**安全结论可审计**；大模型只做话术润色 |

## 第 2 章 实现流水线（我是按这个顺序做的）

### 2.1 数据底座：先让"内容"成为数据，而不是硬编码在页面里

从项目书里把内容抽成结构化数据文件：

- `brand-content.mjs`：品牌故事、品牌 DNA、**六大差异化优势对照表**（项目书表1）、
  市场调研数据（92.6% 看重成分天然等）、痛点条形图数据、助农闭环、合规条款
- `products.mjs`：6 个商品的规格/价格/卖点/参数/用法/包装/价格对比表
- `trace-records.mjs`：2 个溯源批次 × 6 个节点（种植/采摘/冷榨/检测/灌装/物流）
- `knowledge-base.mjs`：五大类应答策略、16 条问答、意图关键词、**症状分级规则**、
  **医疗红旗症状**、情绪关键词、免责声明

**为什么先做这一步**：页面、API、AI 客服、小程序都读同一份数据。
后面改文案只改一个文件，四个端同时生效，不会出现"网页改了、小程序没改"。

### 2.2 数据库层：抽象接口 + 双驱动

设计要点：

1. **业务 SQL 统一用 `?` 占位符**。SQLite 和 MySQL 的差异在驱动内部消化：
   这个决策后来救了我一次（见 3.4——`URLSearchParams.size` 的坑）。
2. **`node:sqlite` 的 SQL 是同步的，MySQL 是异步的**。所以驱动接口统一返回 Promise，
   查询封装成 `await query()/get()/run()`，业务层不用关心底层是同步还是异步。
3. **事务也统一**：提供 `txBegin/txCommit/txRollback`，业务侧写 `await withTransaction(async () => {...})`。
4. **MySQL DDL 自动转换**：`mysql-ddl.mjs` 把 schema.sql 里的
   `TEXT`（索引列→`VARCHAR(191)`，其余→`LONGTEXT`）、`AUTOINCREMENT`、`REAL` 等自动改写，
   一份表结构两套数据库都能建。

### 2.3 后端 API：分域路由 + 统一错误处理

- `server.mjs`：极简 HTTP 服务，同时负责 **API 路由 + 静态资源 + 前端托管 + 统一错误响应**
- `http/`：响应体规范 `{code, message, data}`、请求体解析、登录态（HMAC-JWT）与权限
- `routes/`：catalog / cart / order / user / trace / ai / admin / dev 八个域
- `services/`：真正的业务逻辑，路由只做参数校验和转发

**为什么把 services 和 routes 分开**：路由薄、逻辑厚，方便写自检脚本直接调 service，
也方便以后换 Web 框架而不动业务。

### 2.4 一物一码溯源（项目书的核心亮点，实现要点）

```
赋码：newTraceCode() → CY + YYMMDD + 8位随机十六进制
签名：ECDSA(secp256k1) 对 "溯源码|批次号|检验编号" 签名 → 放进二维码 token
扫码：服务端 verifyTraceToken() 验签
       ├─ 验签失败 → 直接判定仿制品，不展示任何溯源信息
       └─ 验签通过 → 查批次 → 查节点 → 校验哈希链 → 组装时间轴
存证：每个节点 hash = SHA-256(前序hash | 节点内容)   ← 哈希链
      扫码时逐节点重算比对，任一处不匹配即报"存证异常"
防伪：记录 scan_count，首次=正品，重复="该码已查询 N 次，警惕二次封装"
```

有一个容易忽略的细节：**防止拿 A 的 token 查 B 的单品码**——
验签通过后还要核对 token 里的批次号与该溯源码实际所属批次是否一致，不一致直接判伪造。

### 2.5 AI 客服：规则引擎为主，安全优先

处理流程（`services/ai.mjs`）：

```
用户输入
  → 文本归一化
  → ① 症状识别（口语短语表 + 分级规则 + 红旗词）
  → ② 意图识别（关键词加权打分，命中越长越具体权重越高）
  → ③ 槽位抽取（月龄/症状/持续时长/部位）
  → ④ 情绪分析（负向词 + 感叹号密度）
  → ⑤ 分支应答：
       命中症状 → 四级分级 + 护理要点 + 缺槽位追问 + 免责声明
       订单类   → 查真实订单与物流
       其他     → 知识库匹配（带意图加成）
       没匹配到 → 兜底引导 + 推荐提问
  → ⑥ 收尾：情绪安抚 → 是否转人工 → 大模型润色（红线时跳过）
  → ⑦ 落库（会话、消息、槽位、情绪标签、转人工原因）
```

**多轮对话怎么实现**：把槽位存在 `messages.safety_json` 里，
下一轮从最近一条 assistant 消息恢复槽位，所以能记住"宝宝 3 个月"这类信息并追问缺失项。

**为什么规则引擎主导、大模型只润色**：
医疗安全结论必须**可复现、可审计、不能被模型自由发挥**。
所以命中红旗（发热/化脓/精神差/拒奶/呼吸异常）时**跳过润色**，保证安全措辞一字不改。

### 2.6 前端：一个人写 SPA 的取舍

- 手写 hash 路由（`#/product/CY-OIL-100`）：刷新不丢、可直接分享链接、不需要服务端 rewrite
- 一个 `store.js` 管 token/用户/购物车角标/toast，用订阅-通知刷新
- 视图按业务域拆 5 个文件：`home / order / trace / ai / me`
- 视觉延续团队自己的小程序原型（报告书图19）：淡黄基底 + 芽绿点缀，底部 5 个 tab

### 2.7 管理后台

单文件后台（`public/admin/admin.js`），8 个模块：
数据看板 / 订单履约 / 商品与库存 / 溯源管理 / 知识库维护 / 人工客服 / 互动日志 / 月度运维。
其中"溯源管理 → 运行溯源全链路自检"和"知识库 → AI 规则回归测试"是**给评委看的现场演示按钮**。

### 2.8 微信小程序工程导出

写了个生成脚本 `export-miniprogram.mjs`：把 13 个页面的 WXML/WXSS/JS 和
52 张图片一起生成到 `miniprogram/`，直接可用微信开发者工具导入。
好处是**web 端和小程序端共用同一套后端 API**，业务逻辑不重复实现。

### 2.9 边做边验证（这是这个项目最重要的方法论）

我不是"写完再测"，而是每完成一块就写一个**能自动跑的验证脚本**，最后形成 5 套：

| 脚本 | 验什么 | 怎么验的 |
|---|---|---|
| `qr-check.mjs` | 二维码生成 + 防伪签名 | 生成后用**独立解码器 jsQR 回读**，比对内容；再篡改 token 验证被拒 |
| `smoke.mjs` | 端到端业务链路（27 项） | 真发 HTTP 请求：注册→加购→算价→下单→支付→分码→扫码→AI→发货→库存 |
| `ui-check.mjs` | 前端 11 个页面渲染 | **Node 里造一个最小 DOM**，真实 import 前端模块执行渲染，断言页面文本 |
| `serve-check.mjs` | 静态托管与启动 | 按浏览器真实路径验证"根路径返回哪个入口""启动后是否真的渲染" |
| `link-check.mjs` | 全站链接 | 把各页面渲染出的所有 href/src 真实请求一遍 |

**为什么 ui-check 要自己在 Node 里造 DOM**：本机沙箱禁止 Node 拉起带管道的子进程
（`spawn EPERM`），装不了 Puppeteer 驱动 Chrome。所以退而求其次——
自己实现一个够用的 DOM（innerHTML/querySelector/事件监听等），
把前端模块真实加载进来执行。虽然覆盖不了 CSS 视觉，但**能捕获真实的运行时错误**，
而且比真浏览器轻量得多、可在一秒内跑完。

## 第 3 章 遇到的具体困难与解决（答辩最容易被追问的部分）

这一章全部是**真实发生过的事故**，不是设想。

### 3.1 自研二维码编码器：算错容量 + 放错格式信息位

**现象**：为了零依赖，我按 ISO/IEC 18004 自己写了 QR 编码器。写完自检时，
用独立解码器 jsQR 回读，**5 个用例全部解码失败**。

**定位过程**（这一步很典型，值得记住方法）：

1. 先怀疑掩码选择：把 8 种掩码都试一遍，和参考库逐模块比对 → 差异仍然 100+ 个模块
2. 缩小范围：按"左上/右上/左下/定时图案/数据区"分桶统计差异 → 发现**数据区差异最多**
3. 直接读格式信息位：手工按标准布局把 15 位读出来，和期望值比对 → 差了一位
4. **找到第一个真 bug**：格式信息位的放置，我漏了第 8 位，并且左右两半（i<8 与 i≥8）处理反了
5. 修完再比 → 还是错。继续追：把数据区按"之字形排布顺序"读回来，
   逐字节和参考实现比对，发现**容量算错了**——我把"数据区总位数/8"当成了总码字数，
   但里面包含末尾"剩余位"（remainder bits，版本 2-6 是 7 位），
   导致我算出的容量偏大，选错了版本

**最终决策**：修到能跑之后，我还是**换成了 npm 的 `qrcode` 包**。理由：
溯源码是要**印在瓶身上、用户真的要扫**的，自研版本虽然修好了，但我没有第二个独立实现来长期保证它；
`qrcode` 是纯 JS、无运行时依赖，且我用 **jsQR 做独立回读验证（5/5 通过）**。
自研版保留为离线环境的图形码回退，页面上会明确显示当前用的是哪个渲染器。

**这个事故的教训**：能用成熟库的地方不要炫技；如果一定要自研，
必须有**独立实现的交叉验证**，不能自己验自己。

### 3.2 `URLSearchParams.size` 不是"size 参数的值"

**现象**：接口 `/api/products?size=100` 永远只返回 1 条数据。

**定位**：单独测分页函数一切正常，但走接口就错。最后把中间值打出来：
`q.size` 返回的是 **1**——因为 `URLSearchParams` 实例上 `.size` 是**参数个数**（我传了 1 个参数），
`.page` 干脆是 `undefined`。必须用 `.get('size')` 取值。

**修复**：改 `pageParams()` 用 `.get()`，并在注释里写明这个坑，防止以后又被改回去。

**教训**：`URLSearchParams`、`FormData`、`Map` 这些对象的属性名很容易和"参数名"撞车。
另外——**一个 bug 可能同时污染多个页面**，所以修完要跑全量自检。

### 3.3 一行重复的函数声明，让整个首页挂掉

**现象**：`node --check` 检查前端文件时发现 `home.js` 里 `goodsCard` 被声明了两次，
浏览器会直接抛 `SyntaxError: Identifier 'goodsCard' has already been declared`，
**整个模块不执行 → 页面白屏**。

**怎么发现的**：我坚持对每个前端文件跑 `node --check`（语法检查）。
这类错误在写的时候完全看不出来（我在文件中间后来又补了一个同名函数），只有工具能查出来。

**教训**：前端没有编译期，**必须用 `node --check` 兜住语法层**。

### 3.4 真正让用户"卡在加载页"的 bug：占位页把应用挡住了

**现象**：用户反馈"长时间停留在加载页面"。而我的自检**全绿**。

**根因**：我早期在 `backend/public/` 放了一个 `index.html` 占位页（写"正在加载"），
而静态资源查找顺序是 **public 优先、frontend 兜底**——
于是浏览器请求 `/` 时命中了占位页，真正的应用入口永远没被加载。

**为什么自检没抓到**（这是最值得反思的地方）：
- `ui-check` 是**直接 import 视图模块**渲染的，绕过了"浏览器到底加载了哪个 index.html"
- `smoke` 只测 API

**两条路各自都对，合起来却有死角**。

**修复**：
1. 服务端强制：`/` 和 `/index.html` **只由 `frontend/index.html` 提供**，public 下的同名文件被显式跳过
2. 新增 `serve-check.mjs`：按浏览器真实路径验证"根路径返回哪个入口""资源能否加载"
   "**真的把应用启动起来，断言渲染出内容而不是骨架屏**"

**教训**：验证要**贴着用户的真实路径**走。测了模块 ≠ 测了用户看到的东西。

### 3.5 用户报"管理后台 404"

**现象**：用户说后台打不开。

**定位**：探测发现 `/admin.html` 是 200，但 `/admin` 和 `/admin/` 是 404
（用户手输了不带后缀的地址）。

**修复**：
1. 加别名 302 重定向：`/admin`、`/admin/`、`/bg` → `/admin.html`
2. 加了"后台地址有误"的友好提示页，不再显示冷冰冰的 404
3. 新增 `link-check.mjs`：**把各页面渲染出的所有 href/src 真实请求一遍**，
   以后任何"点进去 404"都会被自动抓出来

**教训**：和第 3.4 是同一类问题——**功能都对，但"用户点进去的那条路"没被验证**。
所以现在凡是修这类问题，我都会顺手补一条自动检查，而不是只改代码。

### 3.6 测试脚手架自己写出无限递归

**现象**：跑 ui-check 时所有页面都报 `RangeError: Maximum call stack size exceeded`。

**定位**：为了拦截前端请求，我把 `globalThis.fetch` 换成了包装函数，
但包装函数内部又调用了 `fetch` —— 而那时 `fetch` 已经是它自己了，**无限递归**。

**修复**：在覆盖之前先 `const nativeFetch = globalThis.fetch.bind(globalThis)`。

**教训**：猴子补丁（monkey patch）必须先保存原函数。
另外**报错别急着怀疑被测代码**——这次是测试代码的锅，我一开始差点去改前端。

### 3.7 医疗安全问题：怎么让 AI 不乱说话

这是产品层面最大的风险点。用户会问"宝宝发烧起疹子能不能涂这个油"，
如果 AI 答"可以"，后果是真实的健康风险。

**我的设计**：

1. **四级分级**（不是"能用/不能用"两分法）：
   `ok` 可用 / `caution` 谨慎（先问医生）/ `avoid` 患处禁用 / `emergency` 先就医
2. **红旗症状独立判定**：发热、化脓、渗液破溃、精神差、拒奶、呼吸异常、
   皮疹大面积或快速扩散 → 立即建议就医，并明确"诊断前不要在患处涂任何护肤油"
3. **红旗时跳过 LLM 润色**：保证安全措辞不被模型改写
4. **每条症状回答强制附免责声明**
5. **绝不输出诊断结论和用药方案**：只给非诊疗性护理建议
6. **命中红线时把会话标记为需人工跟进**，并在后台工作台可见

**一个细节**：区分"紧急红旗"和"患处禁用"。
一开始我把"渗液/破溃"也归入 emergency，结果轻微破皮也被升级成"立即就医"，
既不准确也让回答变啰嗦。后来把这两个概念拆开：

- 破皮渗液 = `avoid`（患处别涂，完好皮肤可以正常抚触）
- 发热化脓精神差 = `emergency`（先就医）

### 3.8 症状匹配漏掉口语表达

**现象**：AI 回归测试只有 6/10 通过。用户说"脖子褶皱处发红"，
但规则里写的是"褶皱红"，中间隔了字，`includes` 匹配不到。

**根因**：知识库里的症状词是"完整症状名"（如"尿布疹"），
但用户说话是口语化的，而且**语序会变**。

**修复**：
1. 单独维护一份**口语短语表**（`SYMPTOM_PHRASES`），命中即判定为症状类提问
2. 症状规则里增加 `keywords` 字段（部位词 + 通用症状词），与 `patterns` 一起匹配
3. 只命中了通用词（如只说"红"）没命中具体症状时，保守地按 `caution` 处理
4. 把回归用例固化成自动化测试（现在 10/10 通过）

**教训**：中文口语匹配不能只靠长词 `includes`，要**词表 + 分级 + 回归用例**三件套。

### 3.9 环境带来的约束怎么变成设计

| 约束 | 我的应对 |
|---|---|
| 没有 MySQL/Redis | 做驱动抽象层，默认 SQLite/内存缓存，`DB_DRIVER=mysql` 一键切换；MySQL DDL 自动转换 |
| 沙箱禁止拉起浏览器（spawn EPERM） | 改用 Node 自造 DOM 执行前端模块；**并在文档里如实标注未覆盖 CSS 视觉** |
| 上传 GitHub 有隐私风险 | 项目书里嵌了一张**身份证扫描件**（育婴师证书），这类图片**坚决不提交到公开仓库** |
| 演示数据会被改乱 | 提供 `npm run reset`，一秒恢复干净数据 |

## 第 4 章 答辩速查

### 4.1 一句话讲清技术架构

> 前端是零构建的响应式小程序（并已导出标准微信小程序工程），
> 后端是 Node.js 无框架服务，数据库做成**双驱动抽象**——
> 演示时用内置 SQLite 零安装运行，生产时一个环境变量切到 MySQL + Redis，
> 业务代码一行不用改。核心亮点是一物一码溯源（ECDSA 签名 + SHA-256 哈希链）
> 和带医疗安全红线的 AI 客服。

### 4.2 高频问题与回答

**Q：项目书说 Vue/React，你为什么没用？**
A：为了零构建、离线可跑；同时按原计划导出了微信小程序工程，技术路线不变。（详见 1.3）

**Q：MySQL 呢？**
A：做了驱动抽象，`DB_DRIVER=mysql` 即切换，DDL 自动转换。（详见 2.2）

**Q：溯源数据真实吗？**
A：三层：各环节责任人分别录入 → 每节点哈希链存证，改一处后面全断 →
接入联盟链后哈希上链，中心库被改也过不了链上比对。

**Q：AI 会不会乱说？**
A：四级分级 + 红旗先就医 + 红线时跳过模型润色 + 强制免责声明 + 转人工。安全结论由规则引擎出。（详见 3.7）

**Q：怎么保证代码质量？**
A：五套自动自检，全部真实执行：二维码 5/5、端到端 27/27、页面渲染 11/11、静态托管 20/20、链接巡检 15/15。
一条 `npm run verify` 全跑完。（详见 2.9）

**Q：遇到过什么困难？**
A：讲 3.1（自研二维码的两个 bug 与最终取舍）和 3.4（占位页挡住应用 + 自检盲区），
这两个既有技术深度又有反思，是最能体现工程能力的。

### 4.3 演示顺序（6 分钟版见 `路演演示脚本.md`）

首页品牌背书 → 溯源扫码（**现场演示篡改被拒 + 哈希链校验**）→
AI 客服（**现场演示医疗红线**）→ 购买闭环 → 后台看板与运维 → 对照表演示"技术部分做了没有"。

### 4.4 这个项目最值得学的三点方法论

1. **先探测环境再设计**：否则方案可能在本机跑不起来（1.2）
2. **验证要贴着用户的真实路径**：测了模块不等于测了用户看到的页面（3.4、3.5）
3. **能用成熟库就别自研；自研必须有独立实现的交叉验证**（3.1）
